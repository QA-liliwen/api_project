## 第一部分：传参总览——变量池种子 script_vars.json

平台执行多接口测试项时，**所有运行时数据打包成一个 JSON 文件**，随脚本落地到执行现场，脚本自行读取。不走环境变量（同批多脚本无法用进程级变量区分）、不走数据库（执行端可能 Jenkins 隔离、无平台仓库访问权）。

**两级结构**：公共数据（domain/env + 全量角色头）全执行只存一份（`__common__` 键），各脚本键下只放自己的入参——消除"每个脚本平铺复制一份完整种子"的冗余。

数据流：

```text
dispatch_run 组装种子（执行前，一次完成）
    ├─ domain / env              ← DB_Domain（网关域名+app登录域名）/ DB_Env（环境段）
    ├─ user_{角色}_{端} × N      ← 环境全量角色映射 + fetch_tokens 批量登录 + 头模板
    └─ 测试项 script_inputs      ← DB_TestItem.script_inputs（用户配置的入参 JSON）
                    ↓
    script_vars = { "__common__": {domain, env, 全量头},
                    "test_flow_{item_id}.py": {该脚本入参}, ... }
                    ↓
    通道落地（与脚本同目录）
    ├─ 本地:  api_app/data/custom_runs/{run_id}/script_vars.json
    └─ Jenkins: zip 内同名文件，解压后与脚本同目录
                    ↓
    平台存档（永久留痕）: api_app/data/custom_var/{run_id}_var.json
                    ↓
    脚本读取: 同目录 script_vars.json，两级合并 {**__common__, **自己的入参层}
```

种子真实样例（结构示意，token 已截断；run 114 为优化前的旧格式，公共种子平铺在每个脚本键下）：

```json
{
  "__common__": {
    "domain": "devapi1.lingshi.com",
    "env": "vs2",
    "user_zhihui_oss": { "token": "", "serverid": "" },
    "user_zhihui_app": { "DeviceUniqueId": "d91ed0b9-…", "serverId": "", "token": "" },
    "user_exam_oss":   { "token": "462821:…:1201v", "serverid": "1201" },
    "user_exam_app":   { "DeviceUniqueId": "d91ed0b9-…", "serverId": "1201", "token": "462821:…:1201v" },
    "user_org_oss":     { "token": "30956:…:1203v", "serverid": "1203" },
    "user_student_oss": { "token": "30956:…:1203v", "serverid": "1203" },
    "…": "其余 user_* 键（全量下发，该环境 6 角色 × 2 端 = 12 个）"
  },
  "test_flow_3.py": { "自定义入参": "..." },
  "test_flow_7.py": {}
}
```

**关键点**：

- **三方契约**（平台↔通道↔脚本）：文件固定名 `script_vars.json`、与脚本同目录、顶层键 = 脚本落地文件名 `test_flow_{item_id}.py`（公共数据在 `__common__` 保留键）。脚本原名是什么不重要（平台复制/打包时统一重命名），但**顶层索引键由平台按重命名后的文件名生成**，脚本用 `__file__` 反查天然对齐。
- **两级合并**：脚本读取时 `{**__common__, **own}`——公共层一份共享、入参层各脚本独立，同名键以**入参为准（最高优先级）**。
- **向后兼容**：读取端对无 `__common__` 键的旧格式种子天然兼容（公共层为空 → 合并结果 = own 本身），平台与脚本可异步升级。
- 种子只含**当前环境已配置账号的角色**；查 `custom_var/{run_id}_var.json` 可确认本次实际下发了哪些键。

## 第二部分：请求头传参——user_{角色}_{端} 全量整头

**下发规则**：

- 执行时按环境**全量解析**（不按测试项筛选）：角色→账号映射 → 用户名去重 → 批量登录取 token（每账号固定取 oss+app 两端）→ 按头模板组装。环境配了几个角色就下发 `角色数 × 2` 个头键（全在 `__common__` 公共层）。
- 键名：`user_{英文角色}_{oss|app}`，角色值固定六个：`zhihui / exam / content / org / student / afterschool`。

**头结构**（模板字段 + 两个动态值）：

| 端 | 结构 | 说明 |
| --- | --- | --- |
| oss | `{token, serverid}` | 键全小写 |
| app | `{DeviceUniqueId, serverId, token}` | serverId 驼峰 |

- `token`：执行时登录获取（固定密码优先 → 临时密码回落 → 失败降级**空串不拦截**）。
- `serverId`：从 token 末段动态提取（`token.split(':')[-1].rstrip('v')`），随账号归属机构变化（实测 exam=1201、org=1203），**不能硬编码**。

**脚本引用方式（整头占位）**：

```py
'headers': {'__var__': 'user_exam_app'},
```

**关键点**：

- **整头下发、零拼装**：脚本不接触 token/serverId 单值，引用键名即得完整可发请求的头。
- 空 token 的键**保留完整结构**（值空）——脚本引用到就自然 401，失败在报告可见，不中断其他步骤。
- 多角色共用账号时（如 org/student 同账号）两端 token 值相同。
- 换环境/换账号**不改脚本**：账号在平台侧按"环境×角色"维护，脚本只认 `user_{角色}_{端}` 键。

## 第三部分：测试域名传参——domain / env

公共层两个字符串键：

- `domain`：网关域名，如 `devapi1.lingshi.com`（另有 app 登录域名 `DB_Domain.app_server`，仅登录用，不下发脚本）。
- `env`：环境段，如 `vs2`。

**脚本 URL 采用字符串内嵌占位**：

```py
'url': "https://{'__var__': 'domain'}/qbank/{'__var__': 'env'}/exam/exam/listExams",
```

**关键点**：

- 录制产物中的"域名段"和"环境段"要拆成两个占位符——同一服务在 test/pre/prod 环境间只有这两段变化，其余路径不变。
- 单接口通道的 URL 走 `{}/qbank/{}/...` 的 format 模板（平台组装时替换）；多接口脚本通道走 `__var__` 内嵌占位（脚本运行时替换）。两套形态不同，插件生成多接口脚本时**必须用 `__var__` 形态**。

## 第四部分：多接口入参——script_inputs

每个测试项可配置 `script_inputs`（JSON 字符串），平台侧只做容错解析后放入该脚本键下：

```py
script_vars = {'__common__': common_vars}
script_vars[f"test_flow_{item.id}.py"] = inputs   # 只放入参层
```

合并发生在**脚本读取时**：`{**__common__, **own}`。

**关键点**：

- **入参最高优先级**：同名键以入参为准——脚本作者可用入参覆盖平台注入值（如让某脚本打另一个域名）。
- 容错：空/非法 JSON/非 dict 一律降级空 dict，不拦截执行。
- 用途：同一段录制流程，靠入参做可调参数（数量、名称、关键字等），避免复制脚本硬编码。
- extract 运行时提取的变量与注入键同池：脚本内 `variables[extractor['name']] = ...` 写回，后续步骤 `{'__var__': '提取的键'}` 引用——**多接口串联的核心**（A 接口建题拿 id、B 接口用 id 提交）。

## 第五部分：日志记录

**5.1 执行前置信息（log 头部）**——平台组装、四块内容，每次执行都写：

```text
==================== 执行前置信息 ====================
执行时间: 2026-09-18 10:30:00
环境: 测试环境 (env_id=2) | 域名: devapi1.lingshi.com | App登录域名: ...
测试项(3):
  [3] 试卷列表 | 角色: exam | 测试端: app
角色映射(环境 测试环境，共6条):
  exam -> adminexam
  ...
token 获取结果:
  adminexam: oss=462821:…:1201v | app=462821:…:1201v
  adminvswrr: oss=(失败/空) | app=(失败/空)
======================================================
```

写入通道（对脚本透明）：本地执行由平台父进程**直接先写** log 文件再启动 pytest（Windows 子进程 stdout 无追加语义，走 conftest 会被覆盖）；Jenkins 由构建命令 copy zip 内 `run_header.txt` 直写。

**5.2 脚本侧日志规范**（插件生成脚本必须遵守）：

- **不要配置业务 logging / 不要写日志文件**——平台把 pytest 的 stdout/stderr 重定向追加到 `{run_id}_app.log`，用例结果、断言失败详情全靠 pytest 输出落盘。脚本内 `print` 会自然进日志，可用但不建议多打。
- 断言失败信息**自带上下文**：步骤序号+名称、URL、响应前 2000 字符——变量没替换对（URL 残留 `{'__var__'...}` 字面量）时一眼可见。
- 日志文件名由平台管理（`{run_id}_app.log`），前端从执行记录直接链接查看。

**5.3 排查入口**：

1. log 头部：哪个账号哪个端 token 为空（`(失败/空)` 占位）→ "某角色 401"第一站。
2. `custom_var/{run_id}_var.json`：本次下发的**种子原文**（含 token），脚本拿到什么变量以此为准。
3. 执行现场 `custom_runs/{run_id}/`（本地）：脚本副本 + 种子 + junitxml 报告，可手动重跑。

## 第六部分：插件二次开发思路与方向

**6.1 现状与问题**

插件原生产物（录制转代码）**URL 和请求头全硬编码**录制时的真实值：token 过期即全量失效、绑定录制环境无法跨 test/pre/prod、换账号要逐条改。目录中 `6_/7_/8_` 号脚本仍是原生形态（6 号实际未完成平台化）。

**6.2 目标样板**

`api_app/data/custom_scripts/3_test_recorded_api_sequence.py` 已改造为平台版，是后续改造的**标准样板**，三种占位形态齐全：

```py
REQUESTS = [{
    'url': "https://{'__var__': 'domain'}/qbank/{'__var__': 'env'}/exam/exam/listExams",  # 域名/环境段内嵌占位
    'headers': {'__var__': 'user_exam_app'},                                              # 整头占位
    ...
}]
```

**6.3 三条改造规则**（生成器核心逻辑）

1. **URL 占位化**：识别录制 URL 的域名段 → `{'__var__': 'domain'}`，环境段 → `{'__var__': 'env'}`，其余路径保留。
2. **headers 整头占位**：录制的原始 headers dict 整体替换为 `{'__var__': 'user_{角色}_{端}'}`。
   - 角色判定：录制时无法可靠识别业务角色，可默认给一个角色（如 exam）+ 生成后人工核对测试项配置。
   - **端归属判定（有效手段）**：录制头里的 token 前缀与平台头模板的 token 前缀对比——app 模板 token 前缀 `462821`、oss 模板 `728355`，命中即判端。
   - 为什么必须整头替换而不是只改 token：录制头含过期 token、DeviceUniqueId 等临时字段，整头引用才能把维护权交回平台。
3. **变量语义化（可选，二期）**：录制流程中出现的动态业务值（如列表里取第一条的 id）→ 前置步骤加 `extract`、后续步骤引用 `{'__var__': '提取名'}`，消除步骤间硬编码。

**6.4 实现落点——插件三段式管线**

插件现有架构：`原始录制 JSON → normalize（normalize_request）→ correlate（correlate_requests）→ render（render_pytest_script）`。二次开发**不推翻管线，在中间结构（list[dict]）上插步骤**：

| 管线阶段 | 可复用函数 | 二次开发动作 |
| --- | --- | --- |
| normalize | `normalize_request` / `clean_headers` | 清洗录制头（去噪字段），为整头替换做准备 |
| correlate | `correlate_requests` | 识别跨步骤重复值 → extract 引用（规则3） |
| render | `render_pytest_script` | URL 域名/环境段参数化（规则1）、headers 换占位（规则2）、输出平台版脚本 |

**实现路线**：

- **路线 A（首期推荐）**：独立 CLI 后处理工具（如 `platform_pytest.py`）——输入插件渲染产物或中间结构 JSON，应用三条规则，输出平台版脚本。不动插件主线、可独立迭代验证（拿 6/7/8 号脚本当验证对象）。
- **路线 B（二期）**：接入插件管线，render 阶段加平台化开关，录制完成直接产出平台版。

**6.5 生成脚本必须遵守的契约清单**

1. 文件名 `test_*.py`（pytest 收集规则；平台落地时自动重命名，无需关心重命名）。
2. 变量池读取四要素：同目录 `script_vars.json` + `os.path.basename(__file__)` 索引 + **两级合并** `{**__common__, **own}`（公共层+入参层，入参最高优先级；兼容无 `__common__` 的旧格式）+ 双 `or {}` 兜底（无种子也能裸跑调试）。
3. 占位协议 `__var__`：整值引用 = dict 恰好只有 `__var__` 一个键；内嵌占位用正则 `\{\s*['"]__var__['"]\s*:\s*['"]([^'"]+)['"]\s*\}`（兼容单双引号与空格）。
4. 失败语义：**整值引用未命中 = KeyError（硬失败）**——`user_*` 键平台全量下发、有保障；**内嵌未命中 = 保留占位原样（软失败）**——URL 残留字面量请求自然报错，暴露缺哪个键。
5. `extract` 回写变量池，供后续步骤引用；**不要覆盖平台注入键**（同名会被脚本自身后续引用污染）。
6. 日志：不配业务 logging，断言带步骤上下文（见 5.2）。
7. 依赖仅限：同目录文件 + requests + pytest（Jenkins 隔离执行，requirements 固定为 `requests/pytest/pytest-html`）。

**6.6 风险与注意事项**

- **占位符是 Python 源码字面量，不是 JSON 字符串**：`{'__var__': 'xxx'}` 以字面 dict 形态写进脚本源码。任何"二次归一化/序列化"处理（json.dumps→str、repr 往返）都会破坏它——历史坑：headers 占位经二次归一化被 `str()` 破坏成不可解析文本。规则1/2 的替换必须发生在**渲染文本层或 dict 层**，替换后不再做整体序列化。
- 键名对齐：生成器输出的 `user_{角色}_{端}` 必须使用平台六个英文角色值（`zhihui/exam/content/org/student/afterschool`），中文只在展示层。
- 整头引用的角色若该环境未配置账号 → 种子无该键 → KeyError。脚本可选择 `.get(key, {})` 空头兜底（当前样板采用直接取值、硬暴露），二次开发按需选择，倾向硬暴露。
- 生成器**不要自己拼种子文件**：`__common__` 两级结构由平台下发，脚本只负责读取合并；离线调试可手写一份最小种子（`__common__` 放 domain/env/所需头）。
- 录制脚本与平台 conftest 同目录执行（回调、日志头部由平台负责），**不要在脚本里重复实现回调/日志逻辑**。

## 整体流程（二次开发者视角）

1. 平台执行多接口测试项 → 种子落脚本同目录：`__common__` 公共层（domain/env + 全量 `user_*` 头）一份 + 各脚本入参层。
2. pytest 收集脚本 → 脚本两级合并读取种子 → 逐步骤 `resolve_refs` 替换占位（URL 内嵌、headers 整头）→ 发请求 → extract 回写串联。
3. 结果与日志：pytest 输出追加进 `{run_id}_app.log`（头部是平台前置信息），终态 conftest 回调平台。
4. 插件侧按 6.3 三条规则改造生成逻辑（样板 3 号），落点在三段式管线，路线 A（CLI 后处理）起步。
